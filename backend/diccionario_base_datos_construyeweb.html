1. Contexto del Negocio y Normalización del Inventario

El punto de partida del proyecto fue un inventario comercial plano contenido en el archivo INVENTARIO_FERRETERIA_CONSTRUYE.xlsx con 6,952 filas de productos. Dicho archivo reflejaba los vicios clásicos de los reportes tabulares operativos:

  • Desnormalización severa: Categoría, Subcategoría y Clase estaban forzadas en 3 columnas estáticas. De las 6,952 filas, exactamente 6,945 productos no tenían categoría asignada.
  • Monocódigo de barras: Una sola columna para código de barras, imposibilitando distinguir entre la venta de un tornillo suelto, una caja de 100 unidades o un bulto mayorista.
  • Puntos de Venta (PDV) como texto: No existía aislamiento de stock por sucursal física; las existencias estaban centralizadas en un único número plano sin trazabilidad territorial.
  • Sobrescritura de precios: Los costos y precios de venta eran celdas modificables directamente, borrando el historial de costos de adquisición pasados.
Decisión de Diseño 1.1: Migración a Tercera Forma Normal (3NF) y Nullability Estratégico

El esquema descompuso el reporte plano en 15 tablas interrelacionadas. Crucialmente, el atributo productos.categoria_id se definió como NULLABLE. Si se hubiese definido como NOT NULL, la importación de los 6,945 artículos sin categorizar habría fallado por violación de integridad. Esto permite importar todo el catálogo de inmediato y categorizar progresivamente desde Django Admin.

Decisión de Diseño 1.2: Erradicación de Tipos Flotantes — Precisión Fija NUMERIC

Bajo ninguna circunstancia se utilizan tipos IEEE 754 (FLOAT, REAL o DOUBLE PRECISION). En el comercio ferretero nicaragüense, los márgenes de ganancia y el IVA (15%) exigen precisión contable absoluta. Se establecieron dos escalas fijas:
• NUMERIC(14,4): Para costos de compra, precios base y cálculos de IVA. Cuatro decimales protegen contra errores de redondeo acumulativo al prorratear fletes o descuentos por volumen.
• NUMERIC(14,2) y NUMERIC(12,2): Para totales finales facturados, inventario físico y cantidades comerciales.

Decisión de Diseño 1.3: Extensiones PostgreSQL (pg_trgm y citext)

El DDL arranca ejecutando CREATE EXTENSION IF NOT EXISTS pg_trgm; y CREATE EXTENSION IF NOT EXISTS citext;.
• pg_trgm permite búsquedas difusas mediante trigramas (índices GIN). En ferretería, los clientes suelen buscar "esmeril" o "taladro dewalt" con errores tipográficos; el índice idx_productos_nombre_trgm evalúa la similitud en milisegundos.
• citext proporciona tipos de texto que comparan caracteres sin distinguir mayúsculas ni minúsculas. Se aplica en clientes.email y proveedores.email, impidiendo registros duplicados por variaciones de caja.

Decisión de Diseño 2.3: La Lógica de Fraccionamiento Ferretero

En retail general, casi todo se vende en enteros. En una ferretería coexisten artículos discretos (no se puede vender 0.5 martillos ni 1.3 serruchos) con artículos a granel (se despachan 2.5 kg de clavos de 2", 15.5 metros de cable THHN calibre 12, o 0.5 galones de thinner). El atributo es_fraccionable es consultado por Next.js para renderizar inputs numéricos de tipo step="0.01" vs step="1", y por Django para validar que nadie agregue fracciones de artículos indivisibles.

3.3. Índices Estratégicos sobre productos

CREATE INDEX idx_productos_marca ON productos(marca_id); CREATE INDEX idx_productos_categoria ON productos(categoria_id); CREATE INDEX idx_productos_estado ON productos(estado); CREATE INDEX idx_productos_nombre_trgm ON productos USING GIN (nombre gin_trgm_ops);
Decisión de Diseño 3.3: Índice GIN Trigram para el Buscador Web

En un catálogo de 7,000 productos con nombres largos y combinaciones de números y medidas ("Tornillo Hex 1/4 x 2"), una búsqueda estándar con LIKE '%termino%' ejecuta un escaneo secuencial (Seq Scan) que castiga al servidor de base de datos. El índice idx_productos_nombre_trgm utiliza el operador de trigramas de PostgreSQL para resolver búsquedas difusas instantáneamente por índice GIN invertido.

Decisión de Diseño 3.4: Cardinalidad 1 a N en Códigos de Barra

El Excel original existía una sola columna de código de barras. Esto rompía la operación en caja física: cuando un cliente compra una caja entera de bombillos LED o un paquete de 100 tornillos, el cajero escanea el código exterior de la caja, no abre la caja para escanear una pieza individual. Al modelar una tabla 1:N con campo presentacion, el sistema POS de Elizabeth puede reconocer cualquier empaque y realizar la equivalencia correspondiente de forma inmediata.

4. Precios, Fiscalidad y Vista de Tarifas Vigentes

4.1. Tabla producto_precios

Historial inmutable de precios y costos según el patrón Slowly Changing Dimensions (SCD Tipo 2).

Columna Tipo de Dato Restricciones Descripción y Justificación Técnica
id BIGINT PK ALWAYS AS IDENTITY Clave primaria del registro histórico de precio.
producto_id BIGINT FK ON DELETE CASCADE Producto sujeto a la tarifa.

creado_por VARCHAR(120) NULLABLE Auditoría: Identidad del usuario de Django Admin que autorizó la modificación tarifaria.

4.2. Índice Único Parcial: idx_precio_vigente_unico

CREATE UNIQUE INDEX idx_precio_vigente_unico ON producto_precios(producto_id) WHERE vigente_hasta IS NULL;
Garantía Matemática de Unicidad Temporal

¿Cómo garantiza la base de datos que jamás existan dos precios activos simultáneamente para el mismo producto? Un índice único estándar sobre producto_id impediría guardar el historial. La solución elegante es un índice parcial con la cláusula WHERE vigente_hasta IS NULL. Esto permite infinitas filas pasadas con fecha de cierre, pero prohíbe terminantemente insertar una segunda fila activa mientras la anterior no haya sido cerrada formalmente.

4.3. Vista de Acceso Rápido: v_precio_actual

CREATE VIEW v_precio_actual AS SELECT producto_id, costo_promedio, precio_sin_iva, porcentaje_iva, precio_con_iva FROM producto_precios WHERE vigente_hasta IS NULL;

Esta vista desacopla la complejidad del historial temporal respecto a las consultas del frontend. Cuando Next.js o Django REST Framework necesitan los precios vigentes para el catálogo, no ejecutan filtros manuales de fechas: consultan directamente la vista, garantizando velocidad y exactitud.

La Regla de Oro del Kardex: inventario es la Caché, movimientos es la Verdad

En sistemas comerciales robustos, la tabla inventario nunca es la autoridad final: es únicamente una tabla de saldos agregados para que Next.js consulte el stock disponible en 1 milisegundo sin tener que sumar millones de filas. La verdadera autoridad es movimientos_inventario. En caso de discrepancia física o auditoría tributaria, el saldo real de un producto se reconstruye sumando algebraicamente su historial de movimientos.

Por qué un JOIN dinámico a producto_precios destruiría la contabilidad

Un error común de diseño novato es calcular el importe de un pedido pasado haciendo un JOIN a la tabla de productos o precios actuales. Si hoy un saco de cemento cuesta C$ 360 y dentro de tres meses la inflación lo sube a C$ 420, el JOIN recalcularía hacia arriba las facturas pasadas, alterando las declaraciones fiscales y los recibos de los clientes. El snapshot de precios en pedido_items garantiza inmutabilidad legal absoluta.

Integración con Webhooks de Stripe y Transiciones de Estado

El frontend en Next.js nunca marca un pedido como pagado de manera unilateral. Cuando el cliente paga con su tarjeta de prueba en Stripe, la pasarela emite un evento asíncrono seguro (webhook payment_intent.succeeded) hacia la API de Django. El backend valida la firma criptográfica del webhook, actualiza pagos.estado = 'aprobado', transiciona pedidos.estado = 'pagado' y autoriza el movimiento de inventario definitivo (de reserva a venta), liberando las piezas comprometidas.

8. Automatizaciones en Base de Datos: Triggers PL/pgSQL

Para asegurar que los atributos de auditoría temporal (updated_at) no dependan de la memoria del programador ni puedan ser omitidos por consultas manuales desde herramientas como DBeaver o PgAdmin, la lógica de refresco se ejecuta a nivel de motor mediante un disparador nativo en lenguaje PL/pgSQL:

-- 1. Función disparadora que sobreescribe NEW.updated_at con la marca actual CREATE OR REPLACE FUNCTION fn_set_updated_at() RETURNS TRIGGER AS $$ BEGIN NEW.updated_at = now(); RETURN NEW; END; $$ LANGUAGE plpgsql; -- 2. Trigger automático antes de cualquier UPDATE sobre productos CREATE TRIGGER trg_productos_updated_at BEFORE UPDATE ON productos FOR EACH ROW EXECUTE FUNCTION fn_set_updated_at(); -- 3. Trigger automático antes de cualquier UPDATE sobre pedidos CREATE TRIGGER trg_pedidos_updated_at BEFORE UPDATE ON pedidos FOR EACH ROW EXECUTE FUNCTION fn_set_updated_at(); -- 4. Trigger automático antes de cualquier UPDATE sobre clientes CREATE TRIGGER trg_clientes_updated_at BEFORE UPDATE ON clientes FOR EACH ROW EXECUTE FUNCTION fn_set_updated_at();
Por qué un Trigger de Base de Datos supera al auto_now=True del ORM de Django

Django posee la opción auto_now=True en sus modelos. Sin embargo, este mecanismo de software tiene una debilidad conocida: solo se ejecuta cuando se llama al método instance.save() de Python. Si un desarrollador o administrador ejecuta un Model.objects.filter(...).update(...) masivo o corre un script SQL directo en el servidor de base de datos, Django no dispara el auto_now. El trigger nativo de PostgreSQL en schema_construyeweb.sql actúa a nivel de almacenamiento físico (Before Update), garantizando que jamás exista una fila modificada sin su timestamp real.
